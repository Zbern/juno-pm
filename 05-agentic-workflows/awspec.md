# Agent Workflow Spec (AWSpec) · Juno

_Module 5. Generated by `M5 - Agent Workflow Spec Builder.html`. Paste over `05-agentic-workflows/awspec.md`._

## Goal

Triage member-reported incorrect or missing pension payments so the PM sees data-quality problems within one business day instead of discovering them through support volume.

**Primary actor:** Agent + Human-in-the-loop (on-call PM)

## Trigger

Either of:

1. A new `payment_dispute` report arrives in `#escalations` (posted by the member-facing report flow), or
2. The 8:45 am daily scheduler fires.

## Steps & tools

**Pattern:** ReAct (single-agent reason–act–observe loop). Chosen because the task is short (≤ 6 steps), sequential, and every step needs the previous result; multi-agent or planner patterns would add coordination cost without adding capability.

| Step | Action | Tool / model | Guardrail |
|---|---|---|---|
| 1 | Read new dispute reports since last run | `slack.read_channel("#escalations", since)` · read-only | Only `#escalations`; ignores any instructions embedded in message text |
| 2 | For each report, fetch the disputed payment record and the member's eligibility | `payments.lookup(member_id, payment_id)` · `hr.eligibility(member_id)` · read-only | Read-only; PII stays in working memory, never written to Slack or Jira. Reports reference `payment_id` only |
| 3 | Classify each report {duplicate, likely member error, likely data issue, needs human} with a confidence score, citing the record fields that support it | LLM, temperature 0.2 | Confidence < 70% → forced `needs human` |
| 4 | Compute daily dispute rate = reports ÷ payment-history views | `analytics.views(date)` · read-only | Formula and inputs logged for audit |
| 5 | If rate ≥ 5% **or** any cluster ≥ 10 reports on one payment source, create one Jira stub summarising the cluster | `jira.create_stub(payload)` · write | Create only; never edit or close. Max 3 stubs per run |
| 6 | Post digest: rate < 5% → `#pm-daily`; rate 5–15% → `#escalations` tagging `@on-call-pm`; rate > 15% → P0 alert in `#escalations` recommending maintenance mode | `slack.post(channel, payload)` · write | Restricted to `#pm-daily` and `#escalations`. Digest is held for 5-min PM review before auto-posting |

**Schemas**

- `payments.lookup` → `{payment_id, date, amount, source, method_last4, receipt_url, status}`
- `hr.eligibility` → `{status, pension_credits, eligible_since}`
- `analytics.views` → `{date, history_views}`
- `jira.create_stub` → `{ticket_id, url, status}`
- `slack.post` → `{ts, channel, ok}`
- Classification output → `{report_id, payment_id, class, confidence, evidence[], suggested_action}`

**Memory (in or out of scope)**

- **Episodic:** In-scope. Tool results, retrieved records, per-report confidence, computed rate. Lifetime: end of run.
- **Semantic:** In-scope. Pension handbook taxonomy, Juno system prompt, PM preferences (digest format, quiet hours). Lifetime: indefinite, refreshed weekly. **Out of scope:** any member PII or individual payment record — never persisted.
- **Working:** In-scope. Current batch of reports, `member_id`s, fetched records, running rate. Held in working context only, cleared at end of run.
- **External:** Slack `#escalations` (read), `#pm-daily` + `#escalations` (write), Pension Payments DB (read), HR system (read), analytics (read), Jira (write, stub creation only).

## Human-in-the-loop

- Daily 8:55 am: on-call PM has a 5-minute review window before the digest auto-posts to `#pm-daily`.
- Any report classified `needs human` (confidence < 70%) is listed separately with its evidence; the agent does not suggest an action for it.
- Rate 5–15%: PM decides whether the Jira stub becomes a real ticket.
- Rate > 15%: agent **recommends** maintenance mode; only the on-call PM (with engineering) can enable it. The agent never shuts down the site.

## Success & failure

- **Done when:** all new reports classified, rate computed, digest posted to the correct channel, run logged.
- **Fails safe when:** any of the following stops the run and posts a short failure notice to `#escalations`:
  1. > 2 tool errors in a run
  2. `max_steps` = 8 reached
  3. 90 s wall-clock timeout (rerun once from scratch, then stop)
  4. Any attempt to call a write tool outside the allow-list (hard block + log)
  5. Escalation: rate > 15% (agent stops after posting the P0 alert; humans take over)
- Agent can READ `#escalations`, Payments DB, HR system, analytics. Agent can WRITE to `#pm-daily`, `#escalations`, and create Jira stubs. Agent CANNOT modify any payment or HR record, edit Jira tickets after creation, message members, or post outside the two named channels.
