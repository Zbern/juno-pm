# AI-Native User Flow · Juno

## Entry point

**Signal type:** Page or view opened

A member opens the pension portal to check a payment. No "Start AI" click: the moment identity verification succeeds, Juno begins loading the payment history and pre-fetching handbook context for the most recent payment.

**What they see instantly**

Sign-in (username + password), then step-up verification (one-time code). First-time members see a "Register" option. Successful verification lands directly on the payment-history canvas.

## The flow

1. **Verify:** sign-in → step-up verification → `hr.eligibility(member_id)` confirms status. Fail ×3 → lock + support handoff.
2. **Load:** `payments.lookup(member_id, last 5y)` renders the table. Breadcrumb while loading: *"Pulling your payments from the last 5 years…"*
3. **Path A — View only:** member scans, filters, exports. No LLM call. Table is the product; the AI is optional.
4. **Path B — Ask:** member opens the chat bubble or clicks "Why this amount?" on a row → RAG over that payment record + handbook → grounded answer with citations. Breadcrumb: *"Checking the handbook for this deduction…"*
5. **Path C — Report:** from any row, "Report missing / incorrect payment" → structured report → M5 triage agent. Confirmation with a reference number.

## AI moments

**Placement:** Full-Page Canvas for the history; expandable chat bubble for explanations.

The table shows, per payment: date · payment ID · amount · payment method (last 4 digits) · source · receipt link · **Why this amount?** · **Report**. Actions above the table: export CSV / PDF, date-range filter.

Rationale: the primary job is *seeing* the history, which a full-page table serves with the least friction. The AI moment is secondary and contextual: each row carries a "Why this amount?" entry point so members don't have to compose a question from scratch. The chat bubble expands only on click and answers in the format defined in the M1 system prompt (one-line answer, table, cited explanation).

**Latency into transparency:** three breadcrumbs — *"Pulling your payments…"*, *"Checking the handbook…"*, *"Verifying figures against payment PAY-xxxxx…"* — so a 2–4 s wait reads as diligence, not lag.

## Fallbacks

**Kill switch**

- Member-level: "Hide assistant" toggle collapses the chat permanently for that session; the table works without it.
- Row-level: "Report missing / incorrect payment" is persistent on every entry, so a member never has to trust an explanation they doubt.
- Ops-level: feature flag `juno.chat.enabled` turns the LLM path off globally in under a minute without touching the table.

**Training signal**

Every "Report" is logged as a `payment_dispute` event with {payment_id, dispute_type, member's note, whether a chat answer preceded it}. Disputes that follow a chat answer are tagged `post-explanation` and feed the M6 eval set as suspected grounding failures. Aggregate dispute rate feeds the M5 agent.

**Fail-safe**

- Payments DB or identity service down → maintenance page, no partial data.
- Handbook index down → table still loads; chat replies *"I can show your records but can't explain rules right now"* and offers the report flow.
- Chat confidence < 70% → abstain + report offer (never a guess).
